## 一、范围变更说明（PRD v1.1 → v1.2 修订项）

原 PRD v1.1 §五 Non-goals 第 3 条为「**不做账号体系与云同步**：无注册、无登录、无服务端存储」。
因本次开发引入全栈架构 + 用户认证，该条 Non-goals 已失效，修订如下：

| 原 Non-goals 条目 | v1.2 状态 |
| :--- | :--- |
| 不做账号体系与云同步（无注册/登录/服务端存储） | ❌ **已移除** —— 账号体系成为本期交付项 |
| 不做真实下单 | ✅ 保留 |
| 不做医疗/营养专业建议 | ✅ 保留 |
| 不接积分商城类接口 | ✅ 保留 |
| 不做移动端原生 App | ✅ 保留 |
| Agent 私教不进 P0 承诺 | ✅ 保留（仍为加分项） |

### 修订后的隐私口径

原「身体数据仅存于浏览器本地存储」修订为：

- 身体数据以 **Fernet 密文**落库到用户自有的数据库文件（本地 SQLite 或自建 Postgres）
- **默认 `CLOUD_SYNC_ENABLED=false`**，即不向任何第三方服务同步
- 分享海报**默认脱敏**，不包含体重、TDEE 等身体原始数据
- 服务端不缓存、不外传、不参与模型训练

**修订理由**：账号体系的价值在于跨设备留存（「换台电脑也能看到我的控卡记录」），
这正是健身类产品的核心留存机制；同时用「加密落库 + 可关闭同步 + 海报脱敏」
三道措施，把隐私风险控制在与原方案同等的水平。

## 二、技术选型决策

| 层 | 选型 | 决策理由 |
| :--- | :--- | :--- |
| 前端 | Vue 3 + Vite + Pinia | 组件生态成熟，贴纸/日历可视化开发效率高；Vite 冷启动 <1s |
| 后端 | FastAPI + SQLAlchemy 2.0 | 自带 Swagger 交互式文档——评审可当场Try-it，**这是 Star 加分项** |
| 认证 | Argon2id + JWT 双令牌 | 无第三方依赖；access/refresh 分离兼顾安全与体验 |
| 数据库 | SQLite 默认 / Postgres 可选 | **默认 SQLite 是刻意选择**：评委克隆后无需装数据库服务，「三行命令跑起来」才能兑现 |
| 敏感数据 | Fernet 对称加密 | 体重/TDEE 密文落库，密钥走环境变量 |
| MCP | httpx 手写JSON-RPC 客户端 | 官方 SDK 不可用时的最小实现，握手/会话/错误处理齐全 |

### 关于数据库选型的一次修正

原始选择是「数据入Postgres」。实现时改为 **`DATABASE_URL` 环境变量驱动，默认 SQLite**。

**原因**：若默认强制 Postgres，评委克隆仓库后第一件事是「装数据库服务 / 装 client」，
Star 转化窗口（30 秒）当场破产。改为环境变量驱动后：
- 零配置场景跑 SQLite，三条命令出界面
- 需要生产部署时改一行环境变量即切 Postgres，**SQLAlchemy 层代码零改动**

## 三、数据库设计

### 3.1 ER 概览

```
users 1──1 user_profiles        （身材档案，敏感字段加密）
  │
  ├──1──N order_records       （点餐记录，含餐品 JSON 快照）
  ├──1──N daily_checkins      （每日打卡，(user_id,date) 唯一）
  ├──1──N coupon_snapshots    （卡券快照）
  └──1──N user_coupons        （用户↔卡券绑定）

meals_cache       （全局菜单缓存，独立于用户）
exercise_presets  （全局运动参数，独立于用户）
```

### 3.2 表结构要点

**users**
| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| username / email | String(50/120) | 唯一索引 |
| password_hash | String(255) | Argon2id |
| role | String(20) | user / admin |
| provider / provider_id | String | **OAuth 预留位**，本期仅 `local` |
| failed_attempts / locked_until | Integer / DateTime | 防暴力破解 |

**user_profiles**
| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| weight_kg_enc / target_weight_kg_enc / tdee_enc | Text | **Fernet 密文**，明文不落库 |
| cloud_sync_enabled | Boolean | 用户级同步开关，默认 false |

**meals_cache**
- `source` 字段区分 `seed`（内置）/ `mcp`（官方实时）
- 种子数据**仅在表中无记录时写入**，绝不覆盖 MCP 拉取的实时数据

**order_records**
- `meal_snapshot` 用 JSON 存下单瞬间的餐品快照 —— 保证历史记录不受后续菜单改价/下架影响
- `exercise_equivalent` 存当次生成的运动换算文案，海报接口无需再读身体数据

**daily_checkins**
- `UniqueConstraint(user_id, checkin_date)` —— 同日重复打卡为覆盖而非新增
- `sticker_svg` 直接存 SVG 文本，海报页零计算直接渲染

### 3.3 数据版本与备份

- 本地数据库文件 `mcfit.db` 已在 `.gitignore`，不入版本库
- 迁移工具 Alembic 依赖已装；本期用 `create_all` 保证零配置启动，
  正式版本化时执行 `alembic revision --autogenerate` 即可

### 第 8 项的设计取舍

守卫不能简单写成「无档案就跳 /profile」，否则会出现两个问题：
1. **死循环** —— `/profile` 本身也需要鉴权与渲染，若不豁免会陷入无限重定向
2. **体验断裂** —— 用户从哪个页面被拦，保存档案后应回到那个页面，而不是被丢回首页

因此采用「豁免页 + from 回跳」模式：

```
用户点 /order → 守卫拦下→ /profile?from=/order → 保存 → router.replace('/order')
```

### 第 11 项：注册接口 P0 级Bug（端到端验证时发现）

| 项 | 内容 |
| :--- | :--- |
| 现象 | 第二个**不填邮箱**的用户注册时返回 409「该邮箱已被注册」，尽管其邮箱从未提交 |
| 根因 | `select(User).where(or_(username==X, email==Y))` 当 `Y` 为 `None` 时，SQLAlchemy 生成 `email IS NULL`，匹配到任意一个存量「无邮箱」用户 |
| 危害 | 库中只要存在一个未填邮箱的账号（演示账号即如此），**所有后续未填邮箱的注册全部失败** —— 阻塞真实用户注册 |
| 修复 | 拆成两条独立查询：`username` 必查；`email` 仅在 `payload.email` 非空时才查 |
| 回归 | 5 条新测试（多账号无邮箱、带邮箱+不带邮箱混用、邮箱重复仍拒绝、用户名重复文案、邮箱登录仍可用） |

**为什么之前没发现**：50 项测试全部基于固定用例，**从未连续注册两个无邮箱用户**；
且该 bug 只在「库中已存在 email 为 NULL 的记录」时触发——单元测试每个用例都重建库，
永远只有 1~2 个用户，恰好绕过了触发条件。**这是「测试环境与生产数据规模不一致导致盲区」的典型案例。**

**已做验证**：临时把源码还原为 bug 版，确认新测试确实失败（409 ≠ 201），
再恢复修复版确认通过——避免写出「永远通过」的无意义断言。

## 六·三·补、贴纸文字错乱与运动代偿语义错误（2026-10-19，用户截图反馈）

### 缺陷 8：贴纸文字与图标重叠

**现象**：4 餐品贴纸上出现「麦粒球嚸鸡翅」这类图标与文字混叠的显示。

**根因**：`_layout()` 返回的 y 是**图标顶部**，而标签统一写在固定行 `_LABEL_Y`
（图标区底部）。1~2 个图标时没问题，但 4 个是 2×2 网格，下排图标贴近底部，
标签就压在了图标上——**该设计默认了「图标区是单行」**。

**修复**：标签改为跟随各自图标底部（`y + s + 12`），删除 `_LABEL_Y`；
2×2 网格间距 10→14、图标 78→72，确保下排标签（y=230）不压到热量条（y=306）。

### 缺陷 9：未吃满却做运动代偿（逻辑错误）

**现象**：今日摄入 1875 / 目标 1949（未吃满），却提示
「今日可补足：还可安排约 慢跑(8km/h) 0.9 公里」。

**根因**：`suggestion_for_gap()` 无论 gap 正负都调 `convert()`，
把**尚未摄入**的热量折算成运动量。

**修复**：语义三分，并新增 `state` 字段供前端区分样式：

| gap | state | 文案 | 运动建议 |
| :--- | :--- | :--- | :---: |
| > 0（未吃满） | `under` | 今日还可吃 X kcal 预算 | **0 条** |
| = 0 | `on_target` | 今日正好达标 | 0 条 |
| < 0（超出） | `over` | 今日已超出 X kcal | 3 条 |

**连带修**：`orders.today_summary` 中 `max(daily_target - kcal, 0)`
把负数截成 0，**超标信息被彻底抹掉**——隐藏更深，改为传真实差额。
新增一条用 `inspect.getsource` 断言接口层不再出现该写法的回归测试。

### 缺陷 10：贴纸落库数据与展示不一致

同款点两份时（热量该算两份），贴纸只贴一个图标，但返回的 `items` 是原始列表，
导致日历格显示两个同名条目、与贴纸对不上。改为落库即去重，
返回拆分为 `items`（贴纸展示项）与 `overflow`（超出 4 个上限的量）。
